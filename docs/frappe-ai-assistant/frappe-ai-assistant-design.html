1 · Executive Summary

Build a privately-hosted AI assistant that answers questions over a curated, isolated mirror of selected Frappe/ERPNext tables — using structured data, free text, documents, and images — without exposing the production ERP and without per-token API bills.

1.1 Goals

#GoalHow this design meets it
G1Answer questions from ERP structured dataText-to-SQL over a mirror DB (execution-verified)
G2Answer from free text / notesVector RAG over embedded text fields
G3Read documents (invoices, delivery notes)OCR via VLM or dedicated engine → structured fields
G4Image Q&A (describe / understand photos)Vision-language model (same brain)
G5Identify pests from photosDedicated fine-tuned CV classifier (Track B)
G6Data isolation — model never touches productionOnly selected tables sync to a separate box the model sees
G7No cost until provenAll evaluation on free tiers; pay only to deploy the winner

1.2 The free-first principle

Decouple evaluation from production. Choosing a model is a one-off experiment; it does not need a paid, isolated box. We screen and validate every candidate on free infrastructure using synthetic data, and spend the first real money only when we already know which model to deploy. This document scopes the free phase on Lightning AI.

1.3 What "self-hosted only" commits us to

The isolation requirement (G6) rules out hosted APIs as the production brain, because sending even the synced subset to a third party breaks isolation. Production therefore needs a GPU box we control (rented ~16 GB to start). But — see §6 — the comparison is still free because it runs on synthetic data on free compute.

1.4 Deliverables of the free phase

  • A scorecard ranking VLM candidates on SQL accuracy, RAG quality, OCR, image-Q&A, latency and VRAM fit → one recommended brain + runner-up.
  • A pest classifier with a per-pest accuracy report, trained on public data.
  • A reusable harness and Lightning Studio environment, ready to re-run when new models appear.

Recommended primary candidate (updated July 2026): Qwen3-VL-8B-Instruct supersedes Qwen2.5-VL as the model to beat. It's the current open-source OCR/document leader at this size, still fits ~16 GB quantized, and shares Qwen2.5-VL's tokenizer — so swapping it into our harness is a one-line model-id change. Keep Qwen2.5-VL in the run as the "previous generation" reference to quantify the upgrade.

Fit reality (measured on a 16GB T4, 2026): a 7–8B model in fp16 is ~15 GB of weights alone, leaving no room for the KV cache — so quantized (AWQ/FP8/GPTQ) builds are mandatory on the cheap box. Qwen3-VL-8B, GLM-4.1V-9B-AWQ, InternVL3.5-8B and Qwen2.5-VL-AWQ all fit; MiMo-VL-7B-RL and Pixtral-12B in full precision do not. The Thinking variants (Qwen3-VL, GLM-4.1V, MiMo-VL-RL) emit a reasoning trace — higher accuracy, higher latency/token cost, all captured by the scorecard.

4.5 The model-tier ladder — best fit at every VRAM size

We test at 16 GB (free Lightning), but production can rent bigger cards. The Qwen3-VL family scales cleanly across the whole range, so the winner we prove at 16 GB has a documented upgrade path — the same serve command, a bigger model id, and --tensor-parallel-size N for multi-GPU.

5.1 The small-pest problem — classify vs. detect

A whole-image classifier assumes the pest fills the frame. Real field photos are the opposite: a thrip or aphid is a handful of pixels on a big leaf, so the pest's signal gets averaged away and accuracy drops. This is the classic small-object problem. Three ways to handle it, in increasing effort:

ApproachHowWhen to use
Classify (baseline)Whole image → one label. Push input resolution up (imgsz 320–448) so small pests survive downsamplingClose-up photos where the pest already dominates the frame
Crop-then-classifyTile the image into patches (or crop to the leaf), classify each, keep the most confidentCheap upgrade when pests are small but photos are framed loosely
Detect (localise + label)Train a detector (YOLO-cls → YOLO detection) on IP102's ~19k bounding-boxed images; it finds and labels each pestWide shots, multiple pests, or when you need where not just what
Recommended path: ship the classifier first (it's the fast, free win), and measure per-class accuracy on realistic loosely-framed photos, not just tight crops. If the small pests (thrips, spider mites) score badly, upgrade just those to crop-then-classify or a YOLO detector — IP102 already ships the boxes for it.

5.2 Pest model-size ladder (all CPU-friendly)

Three stages. The first spend of money is Stage 3, by which point the winning model is already proven.

6.1 Why Lightning AI for the free phase

A Lightning "Studio" is a persistent Linux dev box in the browser (VSCode/Jupyter/terminal). Unlike Colab/Kaggle notebooks it keeps your files and installs between sessions, and you toggle the GPU on only when needed.

Free-tier factValue
Monthly credits15, recurring (~80 T4-hours on cheap GPU)
PersistenceFiles/installs survive between sessions
CPU timeEffectively free — do all setup here, burn no GPU credits
Limits1 active Studio, interruptible, ~4-hr restart on free

6.2 The credit-saving split

Rule: build every non-model piece (mirror DB, vector store, retrieval, harness, sync stubs) on free CPU, using a free hosted-API brain (Groq/Cerebras) as a stand-in. Switch the Studio to a T4 GPU only to (a) load the shortlisted quantized VLMs for the final scorecard and (b) fine-tune the pest model. Your ~80 free T4-hrs go entirely to the two things that truly need a GPU.

7.3 Stage 2 — Serve real weights (GPU toggle)

Option A — vLLM (best for Qwen2.5-VL; OpenAI-compatible)

vLLM turns a Hugging Face model into a local OpenAI-compatible server. The full first run is: toggle GPU → confirm the GPU → install (usually already there) → serve (downloads weights) → test text → test an image. Follow the steps in order.

Step 1 — Switch to the T4 GPU and confirm it's attached. This is a hard gate: do not run any later step until it passes. Use the compute selector (top-right of the Studio), wait for the machine to restart, then verify. vLLM will not run on CPU.

nvidia-smi                                  # must list a Tesla T4; if "command not found", you're still on CPU
If you skip this gate, every later step fails with the same misleading error. On a CPU machine vLLM logs Triton is installed but 0 active driver(s) found and then dies with RuntimeError: Failed to infer device type — including on vllm --help, because building the argument parser instantiates the device config. That traceback is not a broken install, a numpy problem, or a bad model name. It means no GPU is attached. Go back to the compute selector. Note that a Studio reverts to CPU after inactivity, so a setup that worked yesterday can produce this today.

Step 2 — Install vLLM (skip if already present). Recent Lightning base images ship vLLM, torch and numpy 2.x pre-installed — check first rather than reinstalling.

pip show vllm | head -2                     # if it prints a version, skip the install
pip install vllm                            # only if not already present

Step 3 — Fix the numpy 2.x conflicts (older base images only; skip if Step 2 reported vLLM already installed).

Why this happens: on older images pip install vllm upgrades numpy to 2.x, but several scientific libraries baked into Lightning's base were compiled against numpy 1.x and crash the moment transformers imports them — you'll see cannot import name 'Inf' from 'numpy' (scipy) or numpy.dtype size changed … binary incompatibility (scikit-learn, then pandas). Do not downgrade numpy — that breaks vLLM and torch, which need 2.x. Upgrade the three stragglers instead, in one command:
# scipy -> scikit-learn -> pandas: the numpy-1.x holdovers transformers imports on startup
pip install -U "scipy>=1.13" "scikit-learn>=1.6" "pandas>=2.2.2"
vllm --help                                 # SUCCESS = prints help text with NO traceback
# "Failed to infer device type" here is NOT a numpy issue — it means Step 1 was skipped.
# If a different package throws "numpy.dtype size changed", read the bottom of the
# traceback for the package name and upgrade it the same way: pip install -U <name>

Step 4 — Load the model (start the server). Leave this terminal running. The first run downloads several GB into ~/.cache/huggingface; later runs reuse that cache and start in seconds. Wait for the line Application startup complete.

vllm serve Qwen/Qwen2.5-VL-7B-Instruct-AWQ \
  --max-model-len 8192 --gpu-memory-utilization 0.92 --port 8000
# --max-model-len 8192        cap context length to keep VRAM within ~16GB
# --gpu-memory-utilization    fraction of GPU RAM vLLM may claim (0.92 = 92%)
# endpoint served at:  http://localhost:8000/v1
Already downloaded? Check with du -sh ~/.cache/huggingface/hub/models--Qwen--Qwen2.5-VL-7B-Instruct-AWQ. If it's several GB, re-running vllm serve reuses it — no re-download. A crash before the fix in Step 3 usually means nothing downloaded yet.

Step 5 — Test it with text (open a second terminal; leave the server running in the first). A JSON reply proves the brain is serving.

curl http://localhost:8000/v1/models        # confirms the model is loaded
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-VL-7B-Instruct-AWQ","messages":[{"role":"user","content":"Reply with one sentence confirming you are working."}],"max_tokens":50}'

Step 6 — Make it look at a picture. This is a vision model, so a message's content can be a list mixing text and an image_url. Prefer sending the image inline as base64 — the server then does no external fetch, which is more reliable and is the same path your OCR tests use for local files.

Don't point at a public URL directly. When image_url.url is a web link, the vLLM server fetches it, and many hosts (e.g. Wikimedia) block automated requests with 429 Too Many Requests → you'll see a code:500 error. Download the image yourself, then embed it as a data: URI instead.
# 6a — download any image locally (browser-like UA avoids 429), then send it INLINE
curl -L -A "Mozilla/5.0" -o test.jpg "https://picsum.photos/512"
IMG=$(base64 -w0 test.jpg)
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"Qwen/Qwen2.5-VL-7B-Instruct-AWQ","messages":[{"role":"user","content":[
        {"type":"text","text":"Describe this picture in one sentence."},
        {"type":"image_url","image_url":{"url":"data:image/jpeg;base64,'"$IMG"'"}}
      ]}],"max_tokens":100}'
# the '"$IMG"' juggling splices the base64 shell variable into the JSON payload
# 6b — a LOCAL image (e.g. a scanned invoice) via the Python client — better for files & OCR
import base64
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")   # local server ignores the key
img = base64.b64encode(open("data/invoice_01.png", "rb").read()).decode()
r = client.chat.completions.create(
    model="Qwen/Qwen2.5-VL-7B-Instruct-AWQ",
    messages=[{"role":"user","content":[
        {"type":"text","text":"Extract the invoice number, date and total."},
        {"type":"image_url","image_url":{"url": f"data:image/png;base64,{img}"}},
    ]}],
    max_tokens=300)
print(r.choices[0].message.content)
This is goals G3 & G4 in one call. Text + image in the same request is exactly how the harness scores OCR (§4.3, "extract fields from this PDF") and image Q&A ("describe this photo"). Same endpoint, same client — you just add the image part.

Step 7 — Stop & save credits. Press Ctrl+C in the server terminal, then toggle the Studio back to CPU. The T4 burns your ~80 free credit-hours; the retrieval work in §7.4 runs on free CPU.

Swapping in the other candidates (§4.1)

Only one model fits 16 GB at a time, so the comparison is a loop: serve → run the eval → Ctrl+C → serve the next. Every model below speaks the same OpenAI-compatible API — reuse the identical curl/base64 and Python from Steps 5–6, only changing the "model" field to match. Start with Qwen3-VL-8B (the recommended primary candidate), then GLM-4.1V.

  --max-model-len 8192 --gpu-memory-utilization 0.92 --port 8000
# Thinking variant (reasoning): swap in Qwen/Qwen3-VL-8B-Thinking

# GLM-4.1V-9B-Thinking (AWQ) — fits comfortably; reasoning VLM
vllm serve dengcao/GLM-4.1V-9B-Thinking-AWQ \
  --max-model-len 8192 --gpu-memory-utilization 0.92 --port 8000 \
  --limit-mm-per-prompt '{"image":4}'

# InternVL3-9B — OCR / document specialist (use an AWQ community build if fp16 OOMs)
vllm serve OpenGVLab/InternVL3-9B --trust-remote-code \
  --max-model-len 8192 --gpu-memory-utilization 0.92 --port 8000

# MiMo-VL-7B-RL (Xiaomi) — top doc/chart scores, but fp16 is TIGHT on 16GB:
# try a shorter context + higher util, or find an AWQ/GPTQ quant; else use the 24GB tier.
vllm serve XiaomiMiMo/MiMo-VL-7B-RL --trust-remote-code \
  --max-model-len 4096 --gpu-memory-utilization 0.95 --port 8000

# Pixtral-12B (Mistral) — needs the mistral tokenizer; 12B wants ~24GB in fp16

If a server dies with CUDA out of memory: the model doesn't fit at that setting. Lower --max-model-len (e.g. 4096), raise --gpu-memory-utilization toward 0.97, or switch to a quantized (AWQ/GPTQ) build of the model. If it still won't fit, that's a scorecard result: this candidate needs the ~24 GB tier.

7.5 OCR (dedicated engine — baseline & modern option)

Baseline (CPU): PaddleOCR is the cheap, no-GPU reference to compare the VLM's built-in OCR against.

Modern option — DeepSeek-OCR-2 (3B, dedicated doc engine): for invoices and delivery notes, a purpose-built OCR model beats a general VLM on structured extraction. DeepSeek-OCR-2 is SOTA on OmniDocBench (~91), small (3B), VRAM-light, and officially supported in vLLM — so it drops straight into the ocr_extract tool of the agentic workflow (§10). Use it when the harness shows the VLM's own OCR isn't accurate enough on real document layouts.

10 · Agentic Workflow — a tool-using brain

The static router in §2 is the v1. The stronger pattern is to let the VLM act as an agent: it plans, calls read-only tools, observes the results, and only then writes a grounded answer — a ReAct-style loop. The same OpenAI-compatible endpoint we already serve supports tool/function calling, so no new infrastructure is needed — just tool definitions and a control loop.

Figure 7 — ReAct loop. The VLM plans, calls read-only tools, observes, and repeats up to N times before synthesizing a cited answer.

10.1 Tools the agent can call

ToolWhat it doesGuardrail
get_schema()Return mirror-DB tables/columns so the model writes valid SQLRead-only metadata
run_sql(query)Execute the generated query on the mirror DBSELECT-only allow-list · read-only DB user · row cap · execution-verified
vector_search(q, k)Semantic search over embedded notes/free-textReturns chunks with source ids for citation
ocr_extract(doc)OCR a PDF/image into structured fieldsDedicated engine or VLM; fields validated vs schema
classify_pest(image)Run the Spec B CV model → pest + confidenceConfidence threshold; abstains below it
final_answer(text, cites)Emit the answerMust include citations (row ids / chunk ids)

10.2 Control loop & guardrails

  1. Plan — the VLM reads the question (+ image) and chooses a tool, or decides it can answer directly.
  2. Act & observe — the tool runs; its result is fed back as an observation.
  3. Loop — repeat up to a hard cap (e.g. N = 4) so a confused model can't run forever.
  4. Synthesize — write the answer grounded only in tool outputs, with citations.
  5. Verify (optional) — a cheap second pass checks the SQL result actually answers the question and every claim is grounded; otherwise re-plan once.
Isolation holds (G6): every tool reads only the curated mirror / vector store / doc store — never production Frappe. SELECT-only + read-only DB user means even a hallucinated query cannot write or reach unsynced data.

10.3 Tiered model roles (this is what makes scale affordable)

One big model answering everything is wasteful. Split the work by difficulty:

RoleModelHandles
Router / plannersmall & fast (Qwen3-VL-4B)Classify intent, route, answer easy lookups directly
Executor / synthesizerQwen3-VL-8B (or 30B)Hard SQL, OCR, multi-step reasoning, final synthesis
Escalation (optional)flagship (235B, multi-GPU)The few genuinely hard queries the 8B/30B gets wrong
Why tiering wins the race: most ERP questions are easy lookups. If the small model handles the bulk and only escalates hard ones, you serve far more users per GPU than routing everything to the big model — the core lever behind the scaling table in §11.

11 · Scaling & the Deployment Race

Testing stays free at 16 GB. Production, though, is a three-way race between model intelligence, GPU budget, and concurrent load. The winner at each stage is the highest-quality model that still meets our latency target at the required concurrency on a fleet we can afford. Low GPU + many users → a smaller, faster model wins on throughput; abundant GPU → a bigger model wins on quality. Spec A's scorecard ranks quality; this section overlays cost and throughput to pick the deployment winner.

11.1 How to size the fleet

Registered users are not concurrent requests. Size on peak in-flight requests:

peak_concurrent ≈ registered_users × peak_active_fraction     # internal ERP tool: ~0.3–1% in busy hours
GPUs           = ceil( peak_concurrent / requests_per_gpu )   # requests_per_gpu comes from a load test
These are planning bands, not promises. Real throughput depends on prompt length, image tokens, output length and quantization — multimodal image tokens cut it sharply. Treat the table as a starting fleet, then confirm requests_per_gpu with a load test (e.g. vllm bench serve) before committing spend. Assumed here: ~800 in / ~400 out tokens, p95 < ~5 s, peak concurrency ≈ 0.5% of users.
